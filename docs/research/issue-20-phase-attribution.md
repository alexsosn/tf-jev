# Research: locate the real schema extraction cost (#20)

The initial frozen BHSA 2021 extraction profiler from PR #34 measured load **45.909s**, full extraction **65.282s**, whole-process peak RSS **4,679,016,448 bytes** and RSS after extract **4,191,952,896**. A later evidence-backed optimization experiment PR #35 streamed per-node JSON hashing through temporary scratch files: its exact same loaded SHA256 **70150b50dab4ba75908146225ec450652256e2471d131f6106cd3bdaac19e82d** proved no identity regression, but its pinned run measured extraction **73.631s**, process peak **4,669,222,912 bytes**, and end RSS **4,188,680,192**. Thus +12.8% time for **only 0.21% peak RSS savings**. The implementation was rejected without merge. Baseline and experiment are independent CI runner runs, not controlled causal proof, but strongly argue against spending more engineering on that particular short-lived JSON allocation.

Current `src/tf_jev/schema.py::_extract` combines: TF metadata discovery, loading all admissible features, raw node→object-type dict materialization and validation, hashing otype/oslots, per-node-feature digest+inventory construction, edge enumeration and digest, source-file hashing and identity, and domain/handle construction. `profile_schema.py` currently measures only *all extraction at once*. The apparently high retained process RSS after extraction suggests large loaded data, Python allocator arenas and exact inventories, not just transient JSON strings. **Measure each phase before optimizing anything else.**

Proposed zero-behavior-change instrumentation: allow an **optional private phase observer** called only after phase boundaries with opaque phase names. It must never see raw nodes/values, never mutate the data or change hash ordering, and must impose negligible overhead when absent. `scripts.profile_schema` records monotonic phase duration, process current RSS, and full process high-water at these boundaries. The same `loaded_sha256` and feature/type inventories should be validated from the real BHSA job, and only aggregate JSON is written/uploaded. The phase durations should approximately sum to the measured `extract_seconds` with only small callback overhead; the first/last boundary must be explicit. Any `/proc` sampling can temporarily allocate memory but is intentionally only at about eight boundaries.

Targets: `discover`, `load_features`, `type_index`, `warp_digest`, `node_features` (hash+inventory; further subdivision after this result), `edge_features`, `source_identity`, `domains`. The new data can guide the next optimization: packed type lookup instead of `node_types` dict, reducing inventory duplication or streamed identity hash. None should be attempted before attribution. Do not treat RSS changes between checkpoints as phase-exclusive allocations or baseline timings as deterministic across runners.
