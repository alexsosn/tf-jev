# Issue #20 — baseline profiling research (2026-10-11)

Inspected `src/tf_jev/schema.py::_extract`, `scripts/probe_corpus_schema.py`, issue #20 and the pinned ETCBC BHSA 2021 workflow. This first increment is **measurement instrumentation**, not an optimization claim.

The extractor calls `TF.explore`, loads *all* admissible features, materializes a raw node→type dict, computes an effective loaded-content SHA-256 over canonicalized arrays of values/metadata and edge endpoints, counts per-(feature, type) inventories and hashes source files separately. Existing BHSA data showed an ~81 s focused test suite and 3,688,204 KiB whole-process RSS in a busy run. Neither is isolated `extract_schema()` cost. In particular a process high-water mark includes fabric loading and other Python allocations; without a controlled baseline it is misleading to label it extractor peak or savings.

**Risk of premature optimization:** replacing loaded-content hashing with a source-file checksum would fail module overlays and in-memory feature-value swaps. Sampling, dropping infrequent values or discarding large inventories would weaken `validate_value` and stale retrieval handles. String non-NFC, empty-string and negative/sparse integer domains must remain byte-exact. Profiling code must not mutate TF loaded feature data or inject monkey-patches. No corpus text/node IDs/feature values should be emitted in profiling reports.

**Instrumentation plan:** Add `scripts/profile_schema.py` that accepts a local TF directory, measures Fabric core load and `extract_schema` separately (one process, monotonic `perf_counter`). On Linux expose both current RSS at stage boundaries from `/proc/self/status` and cumulative peak RSS from `resource.getrusage` labelled *whole-process*, not isolated extractor memory. On platforms without those APIs report `null`. Include the loaded schema digest, TF package version, dataset/version identifier, feature/type counts and relative timings in a compact machine-readable JSON object; omit corpus text and absolute local paths. A separate optional `--trace-python` enables `tracemalloc` for small corpora only; tracing a multi-GiB BHSA snapshot could perturb the benchmark catastrophically. An input `--output` writes the report for CI upload.

**Real data gate:** Use the existing immutable public `ETCBC/bhsa` commit `4db00e2157915495e1a4d3d57e41223df24775da`, sparse `tf/2021` checkout, pinned TF 13.1.0, Python 3.12 Actions. This first runner records a reproducible **baseline** and verifies that the emitted `loaded_sha256` and feature/type counts match expected BHSA truth. Absolute times depend on cache/host/workload and cannot serve as a fixed CI threshold; archive aggregate report with the Actions job for future before/after comparison.

Tests must be RED first for the missing profiling command, then exercise an actual tiny saved TF corpus, JSON validation, stage ordering, time bounds, and no path/corpus text leak. A second ticket iteration can instrument the internal hash/inventory phases and measure an isolated improvement. Do not close #20 without one such measured improvement and independent adversarial review.
