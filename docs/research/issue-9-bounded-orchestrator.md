# Issue #9 research: bounded schema-aware NL parsing vertical slice

2026-10-11. Inspected the current `decisions.py`, `schema.py`, `retrieval.py`, `compiler.py`, `ir.py`, native small-corpus tests and canonical `benchmarks/nl-tf-v2` (109 requests, 57 held out). Issue #9 depends on completed #10; PR #29 separately extends *historical v1* and does not touch this work.

The closed `DecisionBackend` interface yields `DecisionBatch` via `decide(DecisionRequest)`. `DecisionRequest` options are opaque labels, and `validate_answers` enforces exact option membership with probability accounting. However the `DecisionBackend` protocol alone does not guarantee a custom backend validates its own answers: the orchestrator must **revalidate** responses against the exact locally generated question, even if a backend returns an already-constructed `ChoiceDecision`. `ChoiceDecision.confidence` measures separation from uniform; the weakest choice must dominate overall confidence, not an average.

`CorpusSchema` provides expressible node types, node-feature type/domain, enumerated values and identity-bound handles for large domains. It exposes `validate_value`, and `RetrievalIndex.from_schema(...).lookup(..., Match.EXACT)` returns complete bounded candidate sets or refuses truncation. The native compiler already rejects malformed grammar/unknown values/edge types and interpolates only values selected from these attested corpus domains. A corpus value may be non-NFC or contain punctuation; map opaque option labels back to the original bytes, never use backend-provided text as a TF token. Escaped `ascii(value)` is safe as model-facing annotation description without requiring Unicode NFC. Integer range bounds should be a future separate branch; do not invent arbitrary user-extracted thresholds.

The generic issue asks for broad NL parsing, including relations and feature selection over potentially very large schemas. Choosing among hundreds of features in a single Jev question risks hitting backend option limits. **This first PR is a guided vertical slice**: a one-atom query with zero or one equality predicate, requiring a caller-provided *corpus-verified shortlist of features* and optional exact high-cardinality `value_hint` (ordinary caller input, never an unrestricted backend completion). Without a shortlist it can safely generate a bare node-type query; it cannot infer a feature from unconstrained prose. Wider structure selection, relation planning, negation, high-cardinality fuzzy retrieval, one-vs-many projection and automatic feature retrieval require future tickets, not fabricated heuristics. Explicit unsupported/ambiguous and low-confidence abstention must happen before any query string is returned.

Security/adversarial risks: a custom backend may forge labels or request-conditioned answer sets; always revalidate. Excess candidate sets must not truncate silently; abstain. Corpus schema details from `schema` form a local trusted source, not downloaded based on user input. An unsupported NL request *can* still be misclassified by an untrusted backend; this API must not claim otherwise. Held-out benchmark requests/gold are deliberately **not read or embedded** by implementation, and no semantic accuracy numbers are claimed. Tests may use tiny synthetic TF corpus only.

Targets for RED-first tests: deterministic ScriptedBackend success on type-only and enumerated feature/value, schema symbol provenance, role-specific decision evidence and conservative min confidence; exact high-cardinality retrieval with no candidate loss; feature-option overflow abstention; unsupported/ambiguous and low-confidence mode aborts; backend forgery test; actual native compiler execution on tiny TF; byte-identity of unsafe corpus values; no dynamic import/network. Test-first, full Python matrix, and independent adversarial review before merge.

Separate next subtask likely needed: schema-scoped feature candidate retrieval/semantic disambiguation that is model-friendly without dumping large feature inventories. Keep #9 open after this slice.
