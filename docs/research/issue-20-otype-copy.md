# Research: eliminate redundant otype dictionary copy (#20)

Actual pinned Text-Fabric 13.1.0 source `annotation/text-fabric@v13.1.0/tf/core/nodefeature.py` shows `NodeFeature.__init__` stores `self.data = data` and `NodeFeature.items()` returns `self.data.items()`, without transformation. This is the code behind both `api.F.otype` and ordinary loaded node features. Current `src/tf_jev/schema.py::_extract` creates `node_types = dict(api.F.otype.items())`, unnecessarily cloning the already-loaded authoritative `otype` dictionary. The copy is then used for type counts, native interval checks, edge source/target validation, per-feature type partitioning, and loaded-content digest. Subsequent `sorted(node_types.items())` is still necessary for canonical loaded-content SHA and is not removed.

The extractor contract already disallows concurrent TF corpus mutation during extraction. It stores final immutable type/domain/count snapshots rather than the temporary `node_types` mapping. Therefore borrowing `api.F.otype.data` for the duration of `_extract` has the same stable read semantics and avoids one full-size hash table allocation. It must *not* be retained in `CorpusSchema`. No features, metadata, source hashes, overlays or identities should change.

Test-first gate: in a real saved tiny TF fixture, compute existing full snapshot and exact loaded SHA, then disable the `api.F.otype.items` accessor and repeat extraction. Old implementation necessarily fails; new extraction must preserve byte-identical `loaded_sha256`, identity and JSON plus compiled-native query tuples. The fixture is not a claim of model or BHSA performance.

Real performance gate: pinned public BHSA 2021 schema-profile workflow already asserts historical full digest `70150b50dab4ba75908146225ec450652256e2471d131f6106cd3bdaac19e82d`, feature counts, selected/full profile and exact 73,710 compiled/native verb tuples. Compare whole-process RSS/phase times in this job to prior ~4.68 GiB full peak, accounting for CI runner noise; accept only exact native compatibility and measured benefit, not an unsupported claimed speedup. This optimization removes a single redundant dictionary and does not address the much larger JSON serialization allocations.
